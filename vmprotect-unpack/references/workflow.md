# 工具、定位与修复

## 随附脚本

将 `$skillDir` 设置为当前技能安装目录，依赖 pefile 放到任务虚拟环境或本地依赖目录后运行。输出目录必须尚不存在，避免覆盖旧证据。

```powershell
python "$skillDir\scripts\pe_inventory.py" .\sample.exe --out .\analysis\original
python "$skillDir\scripts\pe_inventory.py" .\output\sample.unpacked.exe --out .\analysis\candidate
# case.bin 保存原样 stdin 字节；脚本不会自动添加换行。
python "$skillDir\scripts\compare_runs.py" .\sample.exe .\output\sample.unpacked.exe --input .\case.bin --out .\analysis\compare --execute
```

对比脚本记录 stdout/stderr 原始文件及其哈希、输入/EXE 哈希、退出码和超时。`completed_equivalent` 仅在两次正常完成且退出码和输出一致时为真；仍应查看 `both_exit_zero`，两个相同崩溃不算成功。`--cwd` 可固定共同工作目录，默认分别使用各 EXE 的父目录。该脚本不管理目标派生的子进程，目标会派生进程时改用具备进程树生命周期管理的测试器。

PE 检查脚本还输出资源叶节点的类型/ID/语言路径、载荷长度和哈希、异常表实际排序状态及重定位项数。不同版本的末尾节可能是 `.rsrc` 而非 `.reloc`，重建导入时不可凭节序号猜数据用途。对比资源时忽略可合法变化的 RVA，检查资源路径、大小和载荷哈希；若原资源经过加密，则另按解密后的实际内容验证。发现异常范围重叠时记录具体区间与所属节，分析引用及异常语义；不要只为让检查通过而删除条目，也不要把常规输入测试扩大成异常路径完整验证。

## 工具获取与模拟路线

可评估的开源方案：[x86rc/vmp-lazy-unpack](https://github.com/x86rc/vmp-lazy-unpack)。先核对当前 README、提交和支持架构。工具声称的版本支持不是当前样本的成功保证；不提供通用去虚拟化。不要用 Themida/WinLicense 专用工具 unlicense 直接当作 VMProtect 通用解包器。

本技能不捆绑第三方源码、DLL 或样本。将所需版本下载到当前工作区的 tools，校验并保存哈希；依赖使用本地虚拟环境或 `pip --target`，不依赖作者电脑路径。Windows 上必要时将临时目录设在工作区，避免 one-file 工具自解压权限问题；网络失败按执行环境的权限机制处理。

一次验证过的调用形式（运行前以所下载版本的解析器为准）：

```powershell
# 当前目录为任务目录，工具与依赖已经准备好。
$env:PYTHONPATH = "$PWD\tools\pylibs;$PWD\tools\vmp-lazy-unpack"
python -u -m unpack .\sample.exe sample.stage1.exe --diagnostics *> .\analysis\unpack.log
```

此版本第二个参数只接受文件名，不接受目录路径。实际输出可位于工具自身的 output 目录，应读取日志或 summary.json 的 analysis_pe 字段定位，不猜测输出位置。32 位选项和 imports_only 模式以当前源码为准；不把 PE64 用 32 位模式执行。

使用工具随附 catalog 可以避免抓取宿主 DLL，尤其适合文件访问范围受限的任务；先确认 catalog 与模拟架构一致。不要在缺 catalog 时默许工具自动读取范围外的系统目录。

遇到 `unknown_import` 时先读取事件详情，不用统一返回成功绕过。旧版样本可能需要兼容层，见 [legacy-compat.md](legacy-compat.md)。如果进入 MessageBox 错误路径，先提取文本并检查模拟环境是否缺字段；显示“检测到调试器”不必然代表真实附加了调试器。未建模接口与保护主动拒绝执行应分别诊断。

阶段性产物应包含输入信息、progress、events、summary、导入修复明细。监测当前地址、基本块数量、恢复页数和文件扫描指针；重复循环也可能在顺序计算文件 CRC，不能只看同一条指令就认定死循环。若状态不再变化且可复现，分析循环终止条件或未建模 API 后再重试。

如果异常堆栈显示失败发生在可选诊断 JSON 的临时文件替换（如 `ntdll-reads.json.tmp` 的 WinError 5），应将其记录为宿主日志 I/O 问题，不能据此宣布版本不支持或篡改被模拟 API。保留失败目录后，可在新运行目录取消 `--diagnostics` 重试；常规 progress、events、summary 和导入重建记录仍可用于验证。没有证据时不猜测是杀毒软件或其他特定程序锁文件；不要关闭系统防护。详细诊断缺失时在报告中说明，以最终原生测试补充验证。

## 入口与原生调试路线

“进入已写入代码页”是候选入口条件，不是 OEP 证明。反汇编候选位置，跟踪跳转及其上下文，判断是否仍在保护调度、SDK 或环境初始化。

MSVC x64 常见的 CRT 入口包含分配栈、调用 cookie 初始化、释放栈并转入启动代码，但编译优化、链接增量跳板、编译器与版本会改变布局。模式匹配只是候选发现，不能把一次地址或字节签名当作万能入口。绕开初始化可能破坏 TLS、静态构造或 SDK 状态；需要测试和引用分析。

可用随附 `scripts/find_crt_candidates.py sample.stage1.exe --out analysis/crt.json` 按 Machine 选择 MSVC AMD64 或 I386 入口启发式。它仅列出候选 RVA、调用/跳转目标和指令字节，不修改文件；x86 的 call+jmp 模式尤其可能命中无关函数，必须追踪调用目标和 CRT 初始化语义。多个候选可能指向同一启动过程。无匹配不代表没有 CRT 入口，应改用反汇编/动态跟踪。

跨版本时按架构、文件类型、实际保护选项和运行结果建立测试矩阵。Professional/Ultimate 的名称、版本号或相同源程序不能代替样本检查。同一原始程序在不同保护配置下可能恢复出相同 CRT 地址，仍需重新发现并验证。保持输入样本和前一版本交付物分别命名，避免将旧版输出误当成本轮结果。

动态转储时，在原始代码恢复且导入就绪的适当边界保存映像与必要状态，再用 Scylla 或等价工具重建导入。进程地址不能直接写入可重启 EXE；验证转储中没有悬空堆、模块或模拟地址。不要直接保存进程执行到 main 后的全部数据状态而忽略 CRT 重复初始化。

## PE 修复的判定

| 观察 | 检查与处理 |
| --- | --- |
| 自动输出还保留壳入口 | 找到并验证应用入口，不直接信任 stop_reason 的名字 |
| 崩溃访问模拟堆地址 | 确认是否进入了壳跳板、未恢复状态或残留保护调用 |
| 重定位后访问旧 ImageBase | 修复完整重定位覆盖；不能只保留壳的少数 relocation 项 |
| 固定基址不能装载 | 查看实际环境是否要求重定位、地址是否冲突及装载目录有效性 |
| WinError 623 | 不单凭错误文字认定系统 DLL 冲突，结合实际基址与配置排查 |
| 异常路径崩溃 | 校验 .pdata 排序、范围、UNWIND_INFO、链式项和处理器引用 |
| 启动即崩溃或不输出 | 对照 TLS、Load Config、CFG 指针、IAT、CRT 状态及真实入口 |

优先完整恢复重定位。只有完整恢复暂不可行、首选基址原生测试通过且用户可接受该限制时，才把固定基址版作为受限交付：清楚记录 ASLR 不可用、基址和可能的装载失败。不要将此案例退路自动应用于所有文件。

做最小变更对比：先测试仅修正入口的候选，再逐项调整有证据的问题。早期壳跳板在 ASLR 下的失败不自动证明最终 CRT 入口也失败；每次改变入口/初始化路线后重新核验这项假设。不要一次清除多个数据目录后将成功归因于其中某一项。

同样，清除 Load Config 可能影响安全 cookie、CFG/XFG 或其他加载器行为。仅当其包含壳特有无效信息、已逐项评估必要字段并验证替代行为时考虑清除或重建；不要机械复制示例脚本的目录置零。

## 调试与行为测试

真实调试验证推荐现有 x64dbg/WinDbg。若编写调试器，按架构定义 Win32 结构和 API 原型，处理进程退出与 DLL 文件句柄；不可把本例硬编码的 x64 DEBUG_EVENT 布局用于 x86。分别记录自然退出、调试超时、强制终止和异常代码。

输入注入后关闭 stdin，确保两种运行模式 EOF 一致，否则程序等待下一行会被误判为反调试挂起。输出捕获不能堵塞被调试进程。终止时需排空调试事件并确认目标退出；只管理本次创建的进程，不按宽泛进程名清理系统程序。

空输入、常见无效输入、边界长度只是最小基线。存在有效输入或关键功能测试时应覆盖；没有有效输入就明确未验证成功分支。SDK 相关功能需单独测，不能从普通主路径推断没有剩余保护依赖。
