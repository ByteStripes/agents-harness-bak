# 参考案例：VMProtect Ultimate 3.9.4

用户提供 `ConsoleApp2Cpp_VMP_Ultimate_3.9.4.vmp.exe`，说明与 3.10.3 案例使用相同原程序和保护参数。DIE 普通签名仍返回 Unknown；版本来自用户，非扫描器识别。

- AMD64 PE；输入 15,312,384 字节；ImageBase `0x140000000`；壳入口 RVA `0x129922F`。
- 原始节布局相同，但保护节为 `.Aka`、`.7pb`、`.NAS`，不可依赖 `.vmp*` 名称。
- 未修改解包引擎，沿用工具归档及随附 catalog；约 248 秒、73,202,559 个基本块，恢复 2,583 个页面。
- 重建 164 个导入、362 处调用和 48 处跳转；11 个普通槽、221 个编码槽。
- 首次进入恢复代码的地址为 `0x1401C7EB8`，位于 `.Aka` 保护代码，不是直接交付入口。
- 用新的只读 CRT 候选扫描脚本独立发现 `0xB45E0` 和 `0xB48B0`，两者转至 `0xB4600`；反汇编及运行验证采用前者。地址相同是该相同原程序案例的结果，不是版本通用偏移。

## 最小变更验证

1. 自动重建产物只改入口，保留 ASLR、重定位目录和 Load Config。
2. 实际装载基址 `0x7FF7D27C0000` 时，执行旧地址 `0x140001A55`，触发 `0xC0000005`。此失败发生在最终选定的 CRT 入口版本，直接支持该候选缺少完整重定位的判断。
3. 只进一步关闭 DYNAMIC_BASE/HIGH_ENTROPY_VA、设置 RELOCS_STRIPPED、清除 relocation 目录。Load Config 保留在 RVA `0x18A6620`、大小 `0x140`。
4. 固定在 `0x140000000` 后，普通五组输入及真实附加调试测试全部通过、退出码 0。自动重建文件到最终文件仅 11 个字节不同，均位于上述 PE 头字段。

本例证明不能把“清除 Load Config”作为所有版本的必需步骤；它未证明保留的壳相关配置在所有环境或路径均无影响。保留的异常表有 4,864 项，实际检查已排序；工具报告 `table_sorted: false` 不应单独解释为“输出未排序”，需检查实际数据。

## 边界

`.text` 线性扫描仍有 74 处指向保护区的直接引用，因此没有删去所有保护段。已恢复三条主要业务提示，但不声称解密了所有运行时字符串。五组测试为空行、abc、123456、32 个零、4,096 个 A；未验证有效密钥分支。原文件调试测试 15 秒无正常输出后被测试器终止；恢复版仅出现系统初始断点并正常结束。3.10.3 的用户虚拟机反馈不自动覆盖此样本。

输入 SHA-256：`729D06C324EEDE81B9B5223B56241F87183FABBEE20768A94314CD2559797A3E`。

自动重建 SHA-256：`8A3E01B60E6A417BBB0B5EEB42D92EBB7D2EA4D45A9EC246581D6C2FD165F978`。

最终 SHA-256：`2FFDAF25B27406C3F74D181C645A000A9F97782E1E7C746194CA7EF30EDF81B3`。

结论：现有流程支持该 3.9.4 样本的可运行恢复，无需新增版本特定解包算法。新增候选发现脚本和最小变更验证提高复用可靠性，不能据此保证所有 3.9.4 文件或其他版本完整去保护。
