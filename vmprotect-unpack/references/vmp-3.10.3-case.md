# 参考案例：ConsoleApp2Cpp

保护版本由用户确认：VMProtect Professional 3.10.3；用户称未选择函数虚拟化及变异。版本不是由 DIE 签名独立识别：DIE 当时返回 Unknown。

## 已获得证据

- AMD64 PE，输入 12,755,456 字节，ImageBase `0x140000000`，壳入口 RVA `0x128A302`。
- `.text` 等原始节磁盘大小为零；模拟解压恢复八个节、2,284 个页面。
- vmp-lazy-unpack 使用 Python hooks，约 427 秒、112,990,816 个基本块；文件校验阶段缓慢但扫描位置持续前进。
- 自动重建 163 个导入，修复 410 处调用/跳转引用。唯一导入数与修复次数不可混用。
- 自动 stop 地址 `0x1401C7F8C` 落在 `.rgG` 的保护跳板。以此启动时访问模拟堆 `0x20000001180` 崩溃，证明不是可直接替代的应用入口。
- 另找到并验证 CRT 入口 RVA `0xB45E0`。该地址**只属于本样本**。
- 案例交付采用固定基址，并清除原壳 Load Config/重定位目录。这是有功能限制的样本修复，**不是默认步骤**。
- 普通运行及真实附加调试器时正常输出并退出码 0；五组无效/空输入与原程序相同。原文件附加调试器后 15 秒无正常输出，测试器终止；未逐条定位触发检查。
- 提示字符串 `Enter your key:`、`Product Activated`、`Wrong ActivateKey :(` 已可直接读取。
- 后续用户反馈：恢复版在其虚拟机内正常运行、可以正常调试、功能正常。属于用户实测反馈；未记录虚拟机产品/版本和逐项测试步骤，不外推到所有虚拟化环境。

## 没有证明的事项

- 未验证有效密钥成功分支。
- 代理未独立复测虚拟机环境；用户反馈支持其测试环境可用，不能声称普遍去除反虚拟机限制。
- `.text` 扫描发现 71 处指向保留保护区的直接引用，因此没有删除所有壳段。
- 未恢复全部 ASLR/重定位能力，也未证明所有 SDK 分支和加密字符串均已恢复。

## 重定位证据的边界

早期候选在非首选基址运行时访问旧基址而崩溃，但当时采用的是保护跳板入口；这不足以单独证明改用最终 CRT 入口后仍必须固定基址。后续样本应先保持装载配置，仅修改有依据的入口并测试，再根据最终候选的实际失败定位重定位问题。不要把早期候选的失败条件直接继承为最终文件的限制。
