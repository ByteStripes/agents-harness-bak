# Lite 3.10.4 x86 实测

版本来自用户说明，DIE 普通签名为 PE32/Unknown。输入 12,277,248 字节，Machine 0x14C、PE32、ImageBase `0x400000`，壳入口 RVA `0x7DB1DB`。与 x64 是不同编译产物。

## 原技能的缺口

原生 x86 工具模式 `--32bit` 能解压，但首次无中间状态运行被人工终止，不能算工具自报失败。改用只读进度记录后，约 788 秒、767,747,970 个基本块，恢复 1,969 页，随后在异常处理路径因 VirtualQuery 未建模而停止。CRC/LZMA 加速候选均为零，主要解压执行经过数亿次 Python 回调。

补充 28 字节 MEMORY_BASIC_INFORMATION32 输出后，又遇到 kernel32!RtlUnwind 别名。将其委托给工具已有 x86 展开器后成功。为减少重跑开销，显式采用选择性回调；不跳过目标指令，但计数以及基于计数的模拟计时有所不同，须按 [x86 流程](x86-workflow.md) 的限制使用。

成功轮约 85 秒，自动 stop `0x570530` 位于恢复后的 `.F#v`。日志 496 是观测回调数，不能宣称只执行 496 个基本块。可移植脚本独立再跑一轮，生成的中间文件 SHA-256 完全相同。

## 修复与验证

恢复 168 个 IAT 项，修复 16 处静态调用及 13 处加载，20 个普通槽、206 个编码槽。422 个包装候选没有被展开（407 个不支持的包装指令、14 个不可映射/受保护内存、1 个非临时区写入），因此不能称为所有调用均已去保护。

x86 候选脚本发现多个 call+jmp 形态，逐步确认 `0x4A7B60` 经 `0x404205` 跳板进入 `0x4A8E20` cookie 初始化，再进入 `0x4A7B70` CRT 启动。采用入口 RVA `0xA7B60`，不是 x64 的 `0xB45E0`。

仅改入口版装载于 `0xA60000` 后，在 cookie 初始化读取旧绝对地址 `0x54D180` 发生访问异常。固定基址后正常；保留 Load Config（目录 RVA `0x1367E40`，目录大小 `0x40`，结构内部 Size 为 `0xC0`）和 SafeSEH 表。SafeSEH 声明 432 项，地址 `0x1767F00`，表已排序、RVA 在映像范围内；并未动态验证全部处理器。

五组空/无效输入与原文件输出、退出码一致，均为 0。64 位宿主通过 Win32 调试事件验证 WOW64 目标，记录 `0x80000003` 与 `0x4000001F` 两个启动断点，恢复版正常退出 0；原保护文件退出 `0xDEADC0DE`。资源载荷一致。`.text` 扫描仍有 463 处保护区直接引用，未删除保护代码。

输入 SHA-256：`07173300F0997531A937D6FAF2C5229E2F665AAE10976963B5DD2BADF1832E2F`。

中间 SHA-256：`6609D8EE14D9B421B2B09C1DF763F8D5073AB1799626AC140420192DEF8938FB`。

最终 SHA-256：`209A195276F2FDBD720FAC63C00A2DB7E848F99DE82C1420C7F88FE2A6B44AA7`。

结论：原技能不能原样完整处理此 x86 样本；加入 x86 API/展开兼容、入口识别和 WOW64 测试后得到可运行恢复版。有效密钥、真实虚拟机、全部 SDK/SEH 路径及完整重定位未验证；不外推为所有 x86 样本均支持。
